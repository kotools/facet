# 🎯 Kotools Facet v1.0 : Specifications

## 😩 Problem

In a typical Kotlin project, a single concept needs a parallel data structure to
communicate with external systems. For example, representing a user accessible
via HTTP that needs persistence would look like this:

```kotlin
data class UserDto(val email: String) {
    fun toUser(): User = User(email)
}

data class User(val email: String) {
    fun toUserDto(): UserDto = UserDto(email)
    fun toUserEntity(): UserEntity = UserEntity(email)
}

data class UserEntity(val email: String) {
    fun toUser(): User = User(email)
}
```

This pattern leads to:

- **Boilerplate code**: Redundant data classes and mappers.
- **Maintenance burden**: A single property change ripples through every layer.

## ✨ Solution

With Kotools Facet, the domain model is the only model. Declare each layer in
it, and Kotools Facet takes care of the rest at compile-time.

```kotlin
// Client code:

@Faceted // Enables compile-time projection processing
data class User(val email: String) {
    // Projection declarations:
    object Dto : BidirectionalFacet<User>
    object Entity : BidirectionalFacet<User>
}

// Generated code:

fun User.toUserDto(): UserDto = UserDto(email)
fun User.toUserEntity(): UserEntity = UserEntity(email)

data class UserDto(val email: String) {
    fun toUser(): User = User(email)
}

data class UserEntity(val email: String) {
    fun toUser(): User = User(email)
}
```

This solution provides several benefits:

- **Single source of truth**: `User` is declared once. No parallel data classes
  and mappers to maintain.
- **Easy maintenance**: Changing one property in `User` propagates across
  projections.

> [!IMPORTANT]
> Kotools Facet is not just another mapper generator.
>
> Classic mapper generators answer _"How do I convert A to B?"_. They require
> `UserDto` and `UserEntity` to exist.
>
> Kotools Facet answers _"Why do I need B at all?"_. It requires only the domain
> model (`User`).

## 📦 Modules and dependencies

Kotools Facet v1.0 ships the following modules:

- `facet-core-dsl` that provides `@Faceted` and `BidirectionalFacet`.
- `facet-core-ksp` that generates projections at compile-time.

It depends on:

- Kotlin **2.2.21**
- Java **17**
- KSP **2.2.21-2.0.5**

## 🛠️ Setup

When released, setup will require a KSP plugin and the modules for your stack:

```kotlin
// In build.gradle.kts file:

plugins {
    id("com.google.devtools.ksp") version "<ksp-version>"
}

dependencies {
    ksp("org.kotools:facet-core-ksp:<facet-version>")
    implementation("org.kotools:facet-core-dsl:<facet-version>")
}
```

## 📝 Specifications

> [!NOTE]
> Each rule in this section is expressed using an [RFC 2119] keyword.

### `@Faceted` annotation

```kotlin
@MustBeDocumented
@Retention(AnnotationRetention.SOURCE)
@Target(AnnotationTarget.CLASS)
annotation class Faceted
```

- A class declaration marked by this annotation is referred to as a _faceted
  class_.
- A faceted class MUST be top-level.
- A faceted class MUST be `public` or `internal`.
- A faceted class MUST be a `data class`.
- A faceted class MUST NOT have type parameters.
- The primary constructor of a faceted class MUST be `public` or `internal`.
- A property in the primary constructor of a faceted class is referred to as
  a _faceted property_.
- A faceted property MUST be `public` or `internal`.
- A faceted property MUST NOT be a `vararg`.
- A faceted property MUST be read-only (`val`).
- A faceted property MUST NOT have a type alias, at any position in its type.
  A type alias declared in a dependency counts too. Some Kotlin/JVM standard
  library types are type aliases; a property using one is rejected.
- A faceted property MUST NOT have a function type, at any position in its
  type. An explicit `FunctionN` spelling counts too.
- A faceted class SHOULD contain at least one _facet_.

### `BidirectionalFacet` interface

> [!NOTE]
> `BidirectionalFacet` declares a two-way projection, with _domain-to-facet_ and
> _facet-to-domain_ mappers. More interfaces will be available in the future.

```kotlin
interface BidirectionalFacet<F : Any>
```

- A class declaration nested in a faceted class and implementing this
  interface is referred to as a _bidirectional facet_.
- A bidirectional facet MUST be `public` or `internal`.
- A bidirectional facet MUST be an `object` or a `data object`.
- The `F` type parameter of a bidirectional facet MUST be its containing
  faceted class.
- The name of the class generated from a bidirectional facet MUST be unique at
  package scope.

### Generated classes

- The class generated from a bidirectional facet MUST be located in the same
  package as the faceted class.
- The class generated from a bidirectional facet MUST be a top-level data class,
  with the same visibility as the facet, with the same properties as the faceted
  class (same visibility and order), and with a name being the concatenation of
  the faceted class's name and the facet (e.g., `User` faceted class + `Entity`
  facet = `UserEntity` generated class).
- The generated class MUST NOT contain a default value, a body property, or a
  secondary constructor.
- Each generated property MUST have the same type as the faceted property,
  including nullability and type arguments. A faceted property whose type is
  another faceted class is copied as-is.

### Mappers

- A bidirectional facet MUST generate a _domain-to-facet_ mapper, declared as an
  extension function of the faceted class. Its name is `to` followed by the
  generated class's name (e.g., `User.toUserEntity()`).
- A bidirectional facet MUST generate a _facet-to-domain_ mapper, declared as a
  member function of the generated class. Its name is `to` followed by the
  faceted class's name (e.g., `UserEntity.toUser()`).
- Each mapper MUST have the same visibility as the facet.
- Each mapper MUST copy every property by name, without transformation.
- The _facet-to-domain_ mapper MUST call the primary constructor of the faceted
  class. An exception thrown by that constructor MUST propagate to the caller.
- Mapping a faceted instance to a facet and back MUST return an instance equal
  to the original.
- A mapper's name MUST NOT collide with a declaration written by the user. A
  collision surfaces as a Kotlin duplicate declaration error.

### Diagnostics

- A violated MUST rule fails the build.
- A violated SHOULD rule reports a warning.
- A generated class name collision surfaces as a Kotlin duplicate declaration
  error.
